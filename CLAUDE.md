# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Sobre o projeto

Plataforma 2D didática para treinar agentes DQN (PyTorch + Gymnasium + NumPy + Pygame). O mapa é fixo; o agente (personagem 0) aprende a coletar moedas e empurrar um adversário controlado por política simples. Há sete algoritmos prontos em `algs/`, selecionados por `--alg`: `alg_dqn` (DQN enxuto), `alg_doubledqn_per_dueling` (Double DQN + PER + dueling), `alg_ppo` (PPO), `alg_a2c` (A2C), `alg_ippo` (PPO independente multiagente: todos-contra-todos ou times, com política compartilhada e crítico local), `alg_mappo` (mesma base multiagente, mas com crítico centralizado — CTDE) e `alg_happo` (atores heterogêneos independentes + crítico centralizado, update sequencial com o fator M). O cenário `collectors-vs-pushers` dá papéis assimétricos aos times (metade só coleta, metade só empurra), com empurrão de meia arena e recarga de 2 s. Documentação e comentários do código são em português — responda e escreva código/comentários em português também.

Repositório git local (branch `main`). Artefatos gerados (`venv/`, `checkpoints/`, `logs/`) são ignorados pelo `.gitignore`.

## Comandos

Use o venv existente em `venv/` (Python 3.10; o README menciona `.venv`, mas o diretório real é `venv`):

```bash
source venv/bin/activate          # ou venv/bin/python diretamente
pip install -r requirements.txt   # só se faltar dependência
pytest -q                         # 147 testes, ~10–30s
pytest tests/test_arena.py::test_reset_step_observation -q   # um único teste
```

Treinar (sem janela por padrão; `--episodes` = episódios **adicionais** ao retomar; `--alg` = sufixo do pacote `alg_*`):

```bash
python train.py --episodes 300                          # algs/alg_dqn (padrão), adversário auto
python train.py --episodes 300 --alg doubledqn_per_dueling
python train.py --episodes 300 --alg ppo                # on-policy
python train.py --episodes 300 --alg a2c                # on-policy
python train.py --episodes 300 --alg ppo --envs 8 --opponent rule  # on-policy vetorizado
python train.py --episodes 300 --alg ppo --envs 8 --overlap --opponent rule  # coleta (CPU) sobreposta ao update (GPU)
python train.py --episodes 300 --render                 # com visualização
python train.py --episodes 300 --opponent random        # adversário aleatório
python train.py --episodes 300 --opponent coins         # adversário que persegue moedas
python train.py --episodes 300 --envs 4 --opponent coins  # vetorizado (exige adversário fixo)
python train.py --episodes 300 --resume checkpoints/latest.pt
python train.py --episodes 300 --checkpoint-dir run1 --resume latest.pt   # retoma de outro dir
python train.py --episodes 300 --stats        # perda/grad/Q por episódio em logs/stats.csv
python train.py --episodes 300 --tensorboard  # curvas/histogramas/obs em logs/runs (abra com tensorboard --logdir logs/runs)
python train.py --episodes 300 --tensorboard --eval-every 10  # + avaliação gulosa periódica em eval/*

# Multiagente (IPPO com crítico local / MAPPO com crítico centralizado)
python train.py --alg ippo --agents 4 --scenario all-vs-all --checkpoint-dir checkpoints/all4
python train.py --alg ippo --agents 4 --scenario teams --teams 2 --checkpoint-dir checkpoints/teams4
python train.py --alg mappo --agents 4 --scenario teams --teams 2 --checkpoint-dir checkpoints/mappo_teams4
python train.py --alg happo --agents 4 --scenario collectors-vs-pushers --teams 2 --checkpoint-dir checkpoints/happo_roles
python evaluate.py --checkpoint checkpoints/teams4/best.pt --episodes 10
python play.py --checkpoint checkpoints/teams4/best.pt --render  # modo espectador
```

Multiagente exige `--alg ippo`, `--alg mappo` ou `--alg happo`, `--agents >= 2` e `--opponent auto` (default); com
`--scenario teams`/`collectors-vs-pushers`, `--agents` precisa ser divisível por `--teams`; no cenário
assimétrico `--teams` também precisa ser par. Na primeira versão
`--envs > 1`, `--overlap` e adversários baseline misturados são recusados.

Ao executar scripts que importam torch, prefixe com `TORCH_CPP_LOG_LEVEL=ERROR` para suprimir o spam de avisos do NNPACK.

Avaliar e reproduzir (política gulosa, sem atualizar pesos; o checkpoint identifica o algoritmo, então `evaluate.py`/`play.py` não têm `--alg`):

```bash
python evaluate.py --checkpoint checkpoints/best.pt --episodes 20
python play.py --checkpoint checkpoints/best.pt --render
python play.py --checkpoint checkpoints/best.pt --opponent checkpoints/long3h/ppo/latest.pt  # outro checkpoint
python play.py --checkpoint checkpoints/best.pt --opponent human  # humano controla o adversário
python play.py --player coins --opponent coins --render   # baseline vs baseline, sem DQN
python play.py --player human --opponent coins            # jogar no teclado (abre janela)
python play.py --player human --opponent coins --skin neon  # --skin escolhe o renderer (auto-descoberto)
python play.py --player coins --opponent coins --record demo.mp4   # grava vídeo (30fps, 640x400)
```

Saídas: `checkpoints/best.pt` e `checkpoints/latest.pt`; `logs/training.csv` e `logs/evaluation.csv`.

## Arquitetura

Três camadas, cada uma importando apenas a camada de baixo:

- **`arena/config.py`** — `ArenaConfig` (dataclass): todos os parâmetros do mundo (física, recompensas, duração do episódio, contagem de oponentes/moedas). Sem dependências externas.
- **`arena/actions.py`** — códigos de ação (fonte única): `STOP=0`, `LEFT=1`, `RIGHT=2`, `JUMP=3`, `PUSH_LEFT=4`, `PUSH_RIGHT=5`, `N_ACTIONS=6`, `PUSH_INTENSITY=3`, `NON_PUSH_ACTIONS=(0,1,2,3)`. Engine, ambiente, políticas e agentes importam daqui.
- **`arena/engine.py`** — `ArenaEngine`: simulação pura (física de plataforma em pixels, respawn, moedas, empurrões), sem nenhuma dependência de Gym/Torch. `Character` e `Coin` são dataclasses mutáveis; `step(actions, dt)` retorna um dict de eventos (`collected`, `deaths_delta`, `coins_transferred`). `PUSH_LEFT`/`PUSH_RIGHT` chamam `push(actor, direction, PUSH_INTENSITY)`; o personagem não anda no mesmo passo em que empurra. O empurrão bem-sucedido respeita `cfg.push_cooldown` (recarga por `Character.push_cooldown`, decrementada a cada substep) e o teto `cfg.push_speed_cap`; com `cfg.agent_roles`, coletor não empurra e empurrador não coleta moeda do mapa. O RNG é `np.random.default_rng(seed)` reseedado em `reset`.
- **`arena/environment.py`** — `ArenaEnv(gym.Env)` envolve o engine. A observação é uma grade semântica channels-first `(5, H, W)` float32: canal 0 = plataformas, 1 = jogador, 2 = oponentes, 3 = moedas, 4 = mortos/respawn (célula de 20px, mapa 640×400 → 32×20). Com `frame_stack > 1` a observação vira `(5*stack, H, W)`; `frame_skip` repete a ação por N substeps. O espaço de ações é `Discrete(6)` (ver `arena/actions.py`): parado, andar ←/→, pulo vertical máximo, empurrar ←/→ com força máxima. A política do oponente vem de `agents/baseline.py`, resolvida por `make_policy()` (nomes `rule`/`random`/`coins` ou instância pronta); a cada passo o env monta um `PolicyContext` (obs pré-passo, personagens, `np_random` e `stacked_obs`) por oponente. `get_state()`/`set_state()` dão o snapshot serializável do ambiente (legado da retomada bit a bit; hoje sem chamadores).
- **`arena/scenario.py`** — `Scenario` (frozen dataclass: `n_agents`, `team_ids`): fonte única do cenário multiagente. `all_vs_all(n)` dá um time por agente; `teams(n, k)` dá times contíguos e iguais (ex.: 4,2 → `(0,0,1,1)`); `collectors_vs_pushers(n, k)` (k par) usa os mesmos times e atribui `roles` (metade `collector`, metade `pusher`). `teammates`/`enemies`/`team_of`/`role_of`/`can_push`/`can_collect`/`spawn_positions` alimentam observação, recompensa e push. `from_config` reconstrói o cenário gravado no checkpoint (`n_agents`, `team_ids`, `agent_roles`).
- **`arena/observations.py`** — `render_grid(engine, cfg, viewer=0, channels=5, team_ids=None)`: monta a grade semântica. Sem `team_ids`, reproduz a grade legada do `ArenaEnv` (canal 1 = índice 0, 2 = demais); no multiagente usa 6 canais (1 = self, 2 = inimigos, 5 = aliados; 4 = mortos).
- **`arena/multi_environment.py`** — `ArenaMultiEnv`: ambiente de ações conjuntas. `reset` devolve `obs (n, 6*stack, H, W)`; `step(actions (n,))` devolve `rewards (n,)`, `terminated (n,)`, `truncated (n,)` e `info` com `agents`/`teams`/`team_ids`. Mantém um frame stack por agente, aplica as penalidades de `STOP`/push miss uma vez por step e agrega a recompensa de time pela **média** dos membros. Com papéis, converte `PUSH_*` de coletor em `STOP` antes do engine (o `info` de cada agente traz `role`). Episódios só truncam por tempo; morte respawna.
- **`arena/renderer.py` + `arena/renderer_*.py`** — skins de visualização: cada arquivo define `ArenaRenderer(cfg)` com `render(engine, elapsed, info=None)`/`close()`. `arena/skins.py` (`list_skins()`/`load_renderer_class()`) descobre as skins pelos arquivos e carrega por sufixo — criar `arena/renderer_dinosaur.py` já habilita `--skin dinosaur` nos entry points (as choices do argparse vêm de `list_skins()`), sem tocar em mais código. O renderer é criado **lazily** em `env.render()` (só com `render_mode="human"`); fechar a janela encerra via `SystemExit`.
- **`agents/baseline.py`** — políticas do adversário, todas com assinatura `act(ctx: PolicyContext)`: `PushRulePolicy` (`rule`: aproxima do jogador e às vezes empurra com `PUSH_LEFT`/`PUSH_RIGHT`), `RandomPolicy` (`random`: sorteia entre `NON_PUSH_ACTIONS` — 0..3, sem empurrões) e `CoinRulePolicy` (`coins`: persegue a moeda visível e pula com `JUMP`). Registro de nomes em `POLICIES`/`make_policy()`; o `rng` vem do contexto (o `np_random` do env), nunca de um gerador próprio.
- **`agents/human.py`** — `HumanPolicy` para o jogador: lê o teclado via pygame (setas/WASD andar, espaço/↑/W pular, Q/E empurrar). Devolve `STOP` se não há sistema de vídeo inicializado. Usada por `play.py --player human` (que ativa o render automaticamente); não entra no registro do env para não puxar pygame no treino.
- **`algs/alg_registry.py`** — infraestrutura comum aos algoritmos: `available_algorithms()` descobre diretórios `alg_*/agent.py` em `algs/`; `load_algorithm(name)` importa o pacote (`algs.alg_<nome>`). Checkpoint pesos-only com `algorithm`, `arch_version`, `n_actions`, `obs_shape`, pesos online/alvo, otimizador, `steps`, `epsilon`, `gamma`, `episodes`, `config` e `extra` — sem buffer, RNGs ou estado do ambiente. `load_checkpoint` valida algoritmo, arquitetura, número de ações e formato da observação **antes** de copiar pesos; `resume=True` restaura otimizador/contadores e põe a rede em `train()`, senão só carrega pesos e põe em `eval()`. `algorithm_from_checkpoint(path)` resolve o pacote pelo campo `algorithm` (checkpoint antigo sem o campo é rejeitado). `apply_env_config(cfg, meta)` aplica `frame_stack`/`frame_skip`, o cenário (`n_agents`/`team_ids`/`agent_roles`) e a física do empurrão (`push_impulse`/`push_speed_cap`/`push_cooldown`) gravados. `CheckpointPolicy(agent)` adapta um agente ao contrato `act(ctx)` (guloso, usando `ctx.stacked_obs` quando há stack) — usada pelo `--opponent auto` e pelos testes.
- **`algs/alg_dqn/model.py`** — `QNetwork(nn.Module)`: CNN (3 conv + ReLU → flatten) + MLP head (128) → `n_actions` Q-valores **diretos**, um por ação. O número de features do flatten é inferido com um forward de zeros no `__init__`.
- **`algs/alg_dqn/replay_buffer.py`** — `ReplayBuffer` uniforme com `deque(maxlen)`: toda transição tem a mesma chance. Guarda a 5-tupla `(state, action, reward, next_state, terminated)` (sem `truncated`); `sample()` converte o deque em lista uma vez para indexação O(1).
- **`algs/alg_dqn/agent.py`** — `DQNAgent` (`algorithm="dqn"`, `arch_version="alg-dqn-v1"`): online + target com **alvo fixo `C=1000`** sincronizado a cada 1000 `learn()` bem-sucedidos; alvo `r + γ·max Q_target(s', ·)`; epsilon-greedy (o `train.py` controla ε pela rampa por episódio; o decay por passo do agente é o fallback com `--epsilon-ramp-episodes 0`), Adam + `SmoothL1Loss`, grad clip 10 (`last_grad_norm` = norma pré-clip). `learn()` retorna `None` enquanto o buffer tem menos que `max(warmup, batch_size)` — `train.py` conta com isso. `q_stats(state)` devolve (média, máx) dos Q-valores online sob `no_grad`; `act_batch(states)` age em lote (treino vetorizado); `head_weights()` devolve a última camada para o histograma do TensorBoard. `td_target(reward, next_q, terminated, gamma)` mantém o bootstrap quando `terminated=0` (truncamento).
- **`algs/alg_doubledqn_per_dueling/model.py`** — `DuelingQNetwork`: mesma CNN; separa `V(s)` (`v_head` → 1) de `A(s, a)` (`a_head` → `n_actions`) e devolve `Q = V + A − média(A)`.
- **`algs/alg_doubledqn_per_dueling/replay_buffer.py`** — `PrioritizedReplayBuffer` **rank-based com α e β**: prioridade = `|erro de TD| + 1e-6`, amostragem proporcional a `rank^-α` (α=0,6), `add(..., priority=None)` herda a prioridade máxima; `sample()` devolve `(s, a, r, ns, term, indices, pesos)` — os índices para `update_priorities` e os pesos de importância `(N·p)^-β` normalizados pelo máximo.
- **`algs/alg_doubledqn_per_dueling/agent.py`** — `DoubleDQNPerDuelingAgent` (`algorithm="doubledqn_per_dueling"`, `arch_version="alg-ddqn-per-dueling-v1"`): **`C=1000`** (a busca mostrou que o PER precisa de target mais estável que o `C=10` do DQN), `double_td_target` usa a online para escolher a ação e a target para avaliar; o loss é `SmoothL1` por amostra × peso de importância, β sobe de 0,4 até 1 em `beta_steps` (100 mil updates) e o erro de TD do batch vira prioridade no PER (`_last_indices` guarda os índices amostrados). `head_weights()` usa o ramo de valor.
- **`algs/alg_ppo/model.py`** — `ActorCriticNetwork`: a mesma CNN, mas com `actor` (logits, um por ação) e `critic` (V(s) escalar); `forward` devolve `(logits, value)`.
- **`algs/alg_ppo/rollout_buffer.py`** — `RolloutBuffer` on-policy em lista, sem amostragem: guarda `(s, a, r, ns, terminated, episode_end)`; `mark_episode_end()` marca a última transição para o GAE não atravessar episódios.
- **`algs/alg_ppo/agent.py`** — `PPOAgent` (`algorithm="ppo"`, `arch_version="alg-ppo-v1"`, `on_policy=True`): ator categórico estocástico no treino e guloso em `act(..., greedy=True)`; `learn()` retorna `None` até o rollout ter `rollout_steps` (1024 por padrão) e então faz 4 épocas de minibatches (`batch_size`), com GAE(λ=0.95), clip 0.2, perda de valor 0.5, entropia 0.01 e grad clip 10. `target` é alias de `online` (não há rede-alvo); `epsilon=0`. `end_episode()` só marca a fronteira; `finish_training()` consome o rollout parcial.
- **`algs/alg_a2c/rollout_buffer.py`** — mesmo buffer on-policy, autocontido.
- **`algs/alg_a2c/agent.py`** — `A2CAgent` (`algorithm="a2c"`, `arch_version="alg-a2c-v1"`, `on_policy=True`): mesma rede actor-critic; `n_steps = batch_size` (64 por padrão), retornos n-step com bootstrap no truncamento e corte na fronteira do episódio; um único passo de otimização por rollout. `learn()` espera `n_steps`; `end_episode()` marca a fronteira e, se o rollout ficou incompleto, faz o update do rabo; `finish_training()` também consome resto. `target` alias de `online`, `epsilon=0`.
- **`algs/alg_ippo/`** — IPPO com **uma rede ActorCritic compartilhada** e um `RolloutBuffer` por agente (`MultiRolloutBuffer`). `IPPOAgent` (`algorithm="ippo"`, `arch_version="alg-ippo-v1"`, `on_policy=True`, `multi_agent=True`): `act_batch` age em lote sobre `(n_agents, ...)`; `learn()` só atualiza quando todos os buffers atingem `rollout_steps` (horizonte por agente); `_update` calcula GAE por trajetória, concatena as transições e normaliza as vantagens no conjunto; `end_episode`/`finish_training` marcam/consomem as fronteiras. `target` é alias de `online`, `epsilon=0`. O checkpoint é o mesmo formato pesos-only e grava `n_agents`/`team_ids` no `config`.
- **`algs/alg_mappo/`** — MAPPO (CTDE): `CentralizedActorCriticNetwork` tem a mesma CNN e o mesmo ator compartilhado do IPPO, mas o crítico recebe as features de **todos** os agentes no mesmo passo concatenadas + one-hot do agente e devolve um V por agente (`joint_values`). `MultiAgentRolloutBuffer` guarda um registro por passo conjunto `(T, n_agents, C, H, W)` — `add_transition(i, ...)` acumula as n chamadas do passo e commita quando todos contribuíram. `MAPPOAgent` (`algorithm="mappo"`, `arch_version="alg-mappo-v1"`, `on_policy=True`, `multi_agent=True`): `act`/`act_batch` usam só a observação local (execução descentralizada); `q_stats` aceita `(C,H,W)` ou `(n,C,H,W)`; o GAE é calculado por agente em CPU e as vantagens são normalizadas no conjunto; cada minibatch é um bloco de passos (`batch_size // n_agents`) em que a CNN roda uma vez e alimenta ator e crítico; `value_clip` opcional (padrão desligado, MSE puro). `target` é alias de `online`, `epsilon=0`.
- **`algs/alg_happo/`** — HAPPO (agentes heterogêneos): `HAPPONetwork` tem um `ActorNetwork` por agente (CNNs independentes) e um `CentralizedCritic` com CNN compartilhada entre agentes + one-hot, devolvendo um V por agente. `HAPPORolloutBuffer` é indexado por passo conjunto, como o do MAPPO. `HAPPOAgent` (`algorithm="happo"`, `arch_version="alg-happo-v1"`, `on_policy=True`, `multi_agent=True`, `accepts_roles=True`): máscara `PUSH_*` para coletores; `_update` recalcula log-probs/valores antigos em chunks, treina o crítico e depois atualiza os atores **em sequência** com `ratio = r_i · M`, onde `M = Π_{j<i} r_j_novo` é recalculado sem gradiente após cada ator. Um único Adam faz todos os passos; zerar os grads garante que cada passo toque só o ator (ou o crítico) corrente. `act_batch` usa o ator de cada índice; `q_stats` usa o crítico central; `head_weights` usa o ator 0. A propriedade `online.features` aponta para a CNN do ator 0 só para o histograma do TensorBoard.
- **Entry points na raiz** — `train.py`, `evaluate.py`, `play.py`: `train.py` importa o pacote via `load_algorithm(args.alg)` e monta `ArenaConfig → ArenaEnv → alg.Agent`, aprendendo **a cada passo** (1 transição → 1 `learn()`, ou 1 a cada `--learn-every K`, padrão 4 no modo de 1 ambiente), não por episódio; em PPO/A2C o `learn()` só atualiza quando o rollout enche (PPO) ou a cada `n_steps` (A2C), e os ganchos opcionais `end_episode(info)`/`finish_training()` marcam a fronteira e consomem o rollout parcial; seeda `random`/`numpy`/`torch` com `--seed`, continua a numeração de episódios ao retomar (via `payload["episodes"]`, com fallback para `extra["episodes_done"]`). A exploração dos algoritmos off-policy é agendada pelo `train.py` com `--epsilon-ramp-episodes` (padrão 150, rampa linear de 1 até `--epsilon-min`, padrão 0,1, contada em episódios **absolutos** para a retomada continuar de onde parou; `0` desliga e volta ao decay por passo do agente); `--warmup` (padrão 1000) adia o primeiro update até o buffer ter transições suficientes; `--learn-every K` faz um update a cada K transições; o default é 4 no modo de 1 ambiente (valor validado, ~3× mais passos por hora) e 1 com `--envs > 1` (lá o update já é por passo do vetor; um K explícito > 1 é recusado nesse modo). Com `--envs > 1` o `main` escolhe o loop: `_train_vectorized` para off-policy e `_train_vectorized_on_policy` para PPO/A2C (coleta em paralelo com `act_batch` e rollout em blocos worker-major; `_append_rollout_segment` fecha cada bloco como fim de episódio e `_rollout_target` usa `rollout_steps`/`n_steps` para dimensionar o update). `--overlap` (só PPO/A2C, exige adversário fixo) usa `_train_on_policy_overlap`: uma thread coleta o próximo rollout com uma cópia CPU da política (`_act_batch_on_cpu`, com `torch.Generator` próprio) enquanto a thread principal faz o update na GPU; a fila `maxsize=1` limita a defasagem a um rollout. O PPO grava o log-prob da coleta (`RolloutBuffer.log_probs_array`) e o update usa esse valor como política de comportamento; por depender do timing da sincronização, o modo não é bit a bit reprodutível. O adversário padrão é `auto` (`AutoOpponent(env, alg, ...)` em train.py: 50 eps `random` → 100 alternando `coins`/`rule` → melhor checkpoint, com 10% de alternância para `random`/`coins`/`rule`/outro `.pt` de `checkpoints/`; fases por **contagem absoluta**, então retomar continua o currículo de onde parou; os agentes oponentes usam o mesmo `alg` do treino; o objeto é criado **antes** do load para `init_from_disk` já o deixar pronto). `--checkpoint-dir` define onde salvar/ler os checkpoints (e resolve `--resume` com nome simples). `--stats` grava `logs/stats.csv` por episódio (perda mín/máx, grad pré-clip, Q online/valor do crítico, buffer) sem consumir RNG — não altera o treino. `--max-hours N` encerra o treino de forma limpa após N horas de parede (checa ao fim de cada episódio, salva o `latest.pt` com o episódio real e consome o rollout on-policy parcial); `time_budget_reached` é o helper testável. `--tensorboard` grava em `logs/runs/<alg>_configs_<opponent>_fs<stack>_fk<skip>_lr<lr>_b<batch>_seed<seed>` escalares por episódio e por passo, histogramas de pesos (conv1 e `head_weights()`) e a observação como imagem (`obs_to_image`); retomar com os mesmos argumentos continua as curvas; `--run-name` sobrescreve o nome; também não consome RNG (verificado byte a byte). `--eval-every N` (padrão 0, desligado) roda uma avaliação gulosa a cada N episódios com um `ArenaEnv` dedicado e seeds fixas (`--eval-seed`, padrão 1000, episódios `seed+i`), contra `--eval-opponent` (padrão `rule`), com `--eval-episodes` (padrão 5); grava `eval/coins_mean|coins_std|reward_mean|reward_std|deaths_mean|deaths_std` no TensorBoard, não consome RNG do treino e é incompatível com `--envs > 1`. `evaluate.py`/`play.py` leem o algoritmo do checkpoint (`algorithm_from_checkpoint`), aplicam `frame_stack`/`frame_skip` da config gravada e criam o agente do pacote certo. `play.py` roda o checkpoint como jogador por padrão, ou uma política baseline com `--player` (`coins`/`random`/`human`; com `human`, o render é ativado automaticamente) sem precisar de checkpoint; o `--opponent` do play aceita `rule`/`random`/`coins`, `human` (teclado, também ativa o render; os dois lados humanos são recusados) ou o caminho de outro checkpoint, resolvido em `resolve_opponent` como `CheckpointPolicy` guloso — se o jogador também for checkpoint, `frame_stack`/`frame_skip` precisam coincidir (`SystemExit` antes de criar o ambiente) e, se o jogador for baseline/humano, a config de observação vem do checkpoint do adversário; no modo humano o `PolicyContext` passa `self_character`/`player_character` para o controle no ar. `--record ARQUIVO.mp4` grava a sessão (imageio + `pygame.surfarray`, captura por passo + frame inicial; ativa o render, e com `SDL_VIDEODRIVER=dummy` grava headless; o writer fecha em `finally`, então fechar a janela no meio não corrompe o vídeo). Com `--alg ippo` ou `--alg mappo` o `main` monta `Scenario` (`--agents`/`--scenario`/`--teams`), grava `n_agents`/`team_ids` no `ArenaConfig` e usa `_train_multi_agent` (ações conjuntas, uma transição por agente, médias por agente no `logs/training.csv`, `train/team<t>/*` no TensorBoard); `evaluate.py` detecta o cenário por `n_agents > 1` e grava uma linha por agente; `play.py` entra em modo espectador e recusa `--player`/`--opponent`, exceto `--player human --human-agent N`: aí o humano controla o agente N (precisa de colega de time no cenário), o colega e os adversários usam o checkpoint, e o render desenha cada substep (30 fps) via `step(..., render_intermediate=True)`, mantendo as decisões a cada `frame_skip` substeps.

- **`scripts/duel_multiagent.py`** — duelo multiagente entre dois checkpoints (ex.: MAPPO × IPPO): valida cenário e formato de observação, atribui um checkpoint por time (`--mappo-team`), age de forma gulosa com seeds fixas e grava MP4 (`--record`, funciona headless com `SDL_VIDEODRIVER=dummy`). É o caminho para comparar snapshots de treinos multiagentes — o `play.py` só roda um checkpoint por vez no modo espectador.
- **`scripts/train_long.sh`** — treino por tempo de parede dos quatro algoritmos em sequência: `HOURS` (padrão 3) por algoritmo via `--max-hours`, mesmo protocolo de seed/oponente/frame stack/batch, avaliação de `best.pt` e `latest.pt` (20 eps, seed 1000) ao fim de cada treino. Grava em `checkpoints/long3h/<tag>` e `logs/long3h/`, com runs do TensorBoard sufixados `_3h`; recusa sobrescrever diretórios existentes.

- **`scripts/compare_onpolicy.sh` + `scripts/summarize_all.py`** — runner reprodutível de PPO/A2C no mesmo protocolo da comparação DQN/Double DQN (seed 7, 100 eps, `rule`, `frame_stack=4`, `frame_skip=3`, `batch=64`, TensorBoard, snapshots `ep050`/`ep100`/`best`, avaliação gulosa de 20 eps com seed 1000). Grava tudo em `logs/compare` e deixa os runs em `logs/runs/<alg>_configs_<opponent>_fs<stack>_fk<skip>_lr<lr>_b<batch>_seed<seed>`; recusa sobrescrever diretórios existentes. O sumarizador lê os quatro algoritmos, usa campos ausentes como `n/d`, calcula deltas pareados contra o DQN e escreve `summary-all.txt`, `training_summary_all.csv`, `evaluation_summary_all.csv` e `comparacao-all.md`. Com `--hours N`, descreve o protocolo por tempo de parede e inclui o checkpoint `latest`/`final` (ausente nos CSVs antigos vira `n/d`).

## Semântica que não é óbvia

- **Ações reduzidas**: 6 ações, com uma única intensidade de pulo e uma de empurrão por direção (as máximas). `JUMP` é vertical puro; o deslocamento horizontal no ar continua possível com `LEFT`/`RIGHT` no passo seguinte. `PUSH_LEFT`/`PUSH_RIGHT` usam `PUSH_INTENSITY=3` e não movem o personagem no mesmo passo. O adversário `random` sorteia apenas `NON_PUSH_ACTIONS` (0..3).
- **Episódios só terminam por truncamento** (45s simulados, `truncated=True`); morte nunca termina episódio. Morrer custa 10 moedas (saldo mínimo 0), 5s inativo e respawn em plataforma aleatória. Não existe mais o conceito de eliminação: a morte de um oponente não rende recompensa nem crédito ao jogador. Recompensas: +1 moeda, −2 morte, −0.1 por step do agente escolhendo `STOP` e −0.1 por step empurrando sem oponente vivo em contato no início do step (`push_miss_penalty`). As duas penalidades são aplicadas uma vez por step, não por substep de `frame_skip`; as demais ações não pagam. Cada empurrão bem-sucedido transfere até `push_coin_transfer` (5) moedas do alvo para quem empurrou (o alvo nunca fica negativo); a transferência entra na recompensa com o peso de `coin_reward`, positiva para quem empurra e negativa para o alvo. `push_coin_transfer=0` desliga; `push_coin_reward` (CLI `--push-coin-reward`, default 1.0) escala só a recompensa das moedas transferidas, sem alterar a mecânica. `pbrs_coef` (CLI `--pbrs-coef`) soma `coef*(pbrs_gamma*Phi(s') - Phi(s))` com `Phi = moedas do time - moedas dos inimigos` (PBRS, preserva a política ótima; `pbrs_gamma` deve casar com o `gamma` do agente, default 0.99). O `_train_multi_agent` loga `train/pbrs_mean` e `train/team<t>/pbrs` no TensorBoard; `--save-every-minutes` grava `<checkpoint-dir>/timed/epNNNNN.pt` e `--video-every-minutes` grava `<checkpoint-dir>/videos/epNNNNN.mp4` a cada N minutos de parede (vídeo guloso em ambiente dedicado, headless com SDL dummy, sem consumir o RNG do treino).
- **Multiagente (IPPO/MAPPO/HAPPO)**: todos os agentes decidem uma vez por `env.step` e a ação é mantida nos `frame_skip` substeps (os adversários baseline do single-agent re-decidem por substep). A observação é egocêntrica: canal 1 = self, 2 = inimigos, 5 = aliados (vazio em todos-contra-todos); cada agente tem o seu frame stack. Em times a recompensa de cada membro é a **média** do time; o `info` guarda a bruta e a agregada. O engine só deixa empurrar inimigos (`eligible`), então aliados nunca são alvo e o `push_miss_penalty` é coerente. O cenário (`n_agents`/`team_ids`/`agent_roles`) fica no checkpoint e não pode mudar na retomada. No IPPO cada agente estima `V` da própria observação; no MAPPO o crítico é centralizado (estado conjunto = features de todos os agentes + one-hot) e só existe no treino — `act`/`act_batch` continuam locais. No HAPPO cada agente tem um ator próprio, o crítico é centralizado como no MAPPO e o update é sequencial com o fator `M`; a máscara de papéis é aplicada na política e repetida no ambiente.
- **Cenário coletores × empurradores**: `--scenario collectors-vs-pushers --teams K` (K par) atribui `collector` aos times `< K/2` e `pusher` ao resto. Coletores não empurram (máscara + `STOP` no `ArenaMultiEnv`) e empurradores não coletam moeda do mapa (o engine pula a coleta para esse papel) — eles ganham só a transferência de `push_coin_transfer` por empurrão. O treino calibra `push_impulse` com `ArenaConfig.push_impulse_for_range(width/2, PUSH_INTENSITY)` (≈436,4 para 320 px a 30 fps), eleva `push_speed_cap` para o impulso não ser cortado e liga `push_cooldown=2.0` s por personagem. A recarga não está na observação (a grade segue sem timers), então o timer é mais uma fonte deliberada de não-Markovianidade.
- **Observação não é Markoviana**: velocidades e timers (respawn, moedas) não estão codificados na grade — simplificação didática deliberada.
- **Sete algoritmos, mesma base**: `dqn` e `doubledqn_per_dueling` são off-policy, usam **C = 1000** (alvo fixo sincronizado a cada 1000 `learn()`; a busca mostrou que 10 é agressivo demais) e compartilham a mesma observação, recompensa e seed. `algs/alg_dqn` usa Q direto, replay uniforme e `max Q_target`; `algs/alg_doubledqn_per_dueling` usa dueling, PER rank-based com α=0,6 e pesos de importância (β 0,4→1) e Double DQN (online escolhe, target avalia). O bootstrap usa apenas `terminated`; truncamento por tempo continua bootstrapping. `ppo` e `a2c` são on-policy, com ator categórico (política estocástica no treino e gulosa na avaliação) e crítico compartilhando a CNN; não há replay nem rede-alvo, então `target` é alias de `online` e `epsilon=0`. PPO usa rollout de 1024, GAE(λ=0.95), 4 épocas e clip 0.2; A2C usa retornos n-step (`n_steps=batch_size`) e um update por rollout, consumindo o rabo no fim do episódio. Ambos aceitam `--envs N` (com adversário fixo): `_train_vectorized_on_policy` coleta em workers paralelos, age em lote e monta o rollout em blocos worker-major fechados como fronteira de episódio para o GAE/n-step não atravessar trajetórias. Os retornos GAE/n-step são calculados em CPU (a recorrência escalar em CUDA sincroniza por passo; no A2C os retornos de 64 passos caem de ~41 ms para ~10 ms e o update de ~45 ms para ~13 ms) e só as vantagens voltam ao device. `ippo` é on-policy e multiagente: uma rede compartilhada, buffers por agente e update concatenado; na primeira versão não aceita `--envs`/`--overlap` nem adversários baseline misturados. `mappo` usa o mesmo laço de coleta, mas o crítico é centralizado (features de todos os agentes + one-hot do agente) e o buffer é indexado por passo conjunto; a política em execução continua local e idêntica em contrato à do IPPO. `happo` usa o mesmo buffer conjunto do MAPPO, mas um ator independente por agente e update sequencial: para o agente `i`, a perda usa `r_i · M_i`, com `M_i = Π_{j<i} r_j_novo` recalculado sem gradiente após cada ator; é o algoritmo para papéis heterogêneos e aplica a máscara `PUSH_*` dos coletores. Sem papéis, é um MAPPO com atores separados.
- **Retomada não é bit a bit reproduzível** (decisão do autor): o checkpoint guarda apenas pesos, otimizador, contadores e metadados; retomar continua a numeração de episódios e o treino, mas buffer e RNGs recomeçam do zero. Retomar exige o mesmo `--alg` e o mesmo formato de observação; checkpoints antigos (`cnn-dqn-*`, 12 ações, sem campo `algorithm`) não carregam (`ValueError`). Coberto por `test_resume_loads_weights_and_continues_episode_numbering` e pelos testes de `test_checkpoint.py`.
- **Seeds**: `train.py` faz `env.reset(seed=args.seed + ep)` por episódio; `evaluate.py` usa `--seed 1000`. O RNG do oponente é `env.np_random`, o do engine é separado. No modo `--overlap` as seeds continuam controlando ambientes e amostragem (gerador próprio do coletor), mas a versão de pesos usada em cada rollout depende do timing da thread: o treino não é bit a bit reprodutível.
- Testes manipulam o engine diretamente (ex.: `env.engine.characters[0].y = ...`) para forçar mortes — essa é a forma esperada de testar a física sem esperar 45s.
- **Adicionar um algoritmo**: crie `algs/alg_<nome>/agent.py` com uma classe `Agent` que cumpra o contrato de `algs/alg_dqn/agent.py` (atributos `algorithm`, `arch_version`, `obs_shape`, `n_actions`, `online`, `target`, `optimizer`, `buffer`, `steps`, `epsilon`; métodos `act`, `act_batch`, `learn`, `q_stats`, `head_weights`). Para um algoritmo on-policy, declare `on_policy = True`, use `target = online`, implemente `end_episode(info)`/`finish_training()` opcionais, um `buffer` com `add(...)`/`mark_episode_end()`/`as_arrays()` (o rollout vetorizado insere transições em blocos por worker) e aceite que `--learn-every > 1` continua recusado com `--envs > 1`. `--alg <nome>` passa a funcionar sem tocar em `train.py`; `evaluate.py`/`play.py` seguem o campo `algorithm` do checkpoint. Para multiagente, declare `multi_agent = True`, aceite `n_agents`/`team_ids` no construtor e exponha `act_batch` sobre o lote de agentes, `add_transition(i, ...)`, `end_episode`/`finish_training` e um `buffer` — por agente (IPPO) ou indexado por passo conjunto (MAPPO/HAPPO, que precisam das observações de todos os agentes para o crítico); o `train.py` despacha para `_train_multi_agent` e `evaluate.py`/`play.py` para `ArenaMultiEnv`. Para usar os papéis do cenário assimétrico, declare `accepts_roles = True` e aceite `agent_roles` no construtor; o `train.py`/`evaluate.py`/`play.py` só passam `agent_roles` para algoritmos que declaram esse atributo.
