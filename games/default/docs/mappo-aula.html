visão geral · a troca

Do IPPO ao MAPPO em uma frase

O ator é o mesmo: uma política compartilhada, local, que decide com a observação egocêntrica. O que muda é o crítico: ele deixa de ser local e passa a ver o estado conjunto.

IPPO · crítico local

V(si) é estimado só com a observação do agente i. Cada agente tem uma trajetória e um buffer; o GAE usa o valor local.

1 ator V local N buffers

MAPPO · crítico centralizado

V(sglobal) vê as features de todos os agentes no mesmo passo, mais um one-hot que diz qual agente está sendo avaliado. O ator continua local.

1 ator V central buffer conjunto
CTDECentralized Training, Decentralized Execution. O crítico centralizado é uma muleta de treino: ele reduz a variância do gradiente porque vê o estado conjunto. Na execução, ele desaparece; cada agente usa só a própria observação.
!O ator não fica centralizado. Se o ator usasse o estado global, a política não poderia rodar de forma independente. O MAPPO move o privilégio de informação apenas para o crítico.

crítico · arquitetura

O crítico centralizado por dentro

A CNN é compartilhada entre ator e crítico. O ator usa 1280 features do agente consultado; o crítico concatena as 1280 features de todos e acrescenta o one-hot.

# model.py: o crítico recebe o estado conjunto
joint = feats.reshape(batch, n_agents * n_features)
shared = joint.unsqueeze(1).expand(
    batch, n_agents, joint.shape[1])
onehot = self.agent_onehot.unsqueeze(0).expand(
    batch, n_agents, n_agents)
critic_in = torch.cat([shared, onehot], dim=2)
return self.critic(critic_in).squeeze(-1)
1×Uma CNN, duas cabeças. O gradiente do crítico também atualiza a base convolucional. As features são calculadas uma vez por agente e servem ao ator e ao crítico.

crítico · dependência entre agentes

O que o crítico vê que o ator não vê

O valor de um agente depende das features dos outros. O teste do pacote verifica exatamente isso: mexa na feature do agente 1 e o V do agente 0 muda.

tests/test_mappo.py
feats = torch.randn(1, 2, net.n_features)
values = net.joint_values(feats)

changed = feats.clone()
changed[:, 1] += 1.0
values_changed = net.joint_values(changed)

# o V do agente 0 muda quando o agente 1 muda
assert not torch.allclose(values[:, 0],
                           values_changed[:, 0])

Por que isso ajuda

O GAE de cada agente usa um valor que incorpora o estado conjunto. Em times, o crítico consegue aprender que uma jogada do aliado muda o valor do agente; o crítico local só vê a própria grade.

!Neste mapa, a grade já é global. O canal de cada agente mostra todos os personagens. O ganho do MAPPO aqui não é “ver o que estava escondido”: é o vetor conjunto de features, a identidade pelo one-hot e a variância menor. Em mapas parcialmente observáveis, o ganho é maior.
×O ator não muda. forward(x) devolve só os logits do ator; joint_values é usado apenas no update. Em act/act_batch, nada global é consultado.
buffer · MultiAgentRolloutBuffer

O buffer vira passos conjuntos

O IPPO tem um buffer por agente. O MAPPO tem um registro por passo conjunto: as observações de todos os agentes no mesmo instante, lado a lado.

def add(self, agent_index, state, ...):
    if index in self._pending:
        raise ValueError("agente duplicado")
    self._pending[index] = (...)
    if len(self._pending) == self.n_agents:
        self._commit()   # um registro conjunto
  • Um registro, n agentes. states tem forma (T, n, C, H, W); ações, recompensas e terminadores têm (T, n).
  • Duplicata é erro. O mesmo agente não pode contribuir duas vezes no mesmo passo conjunto.
  • Duas contagens. n_steps conta passos conjuntos; len conta transições (T·n).
=No loop real, add_transition(i, ...) é chamado uma vez por agente, na ordem 0..n−1. O buffer só grava quando o passo está completo; o crítico centralizado precisa exatamente disso.
buffer · o gatilho do update

O gatilho é o passo conjunto

O IPPO espera todos os buffers por agente. O MAPPO espera o rollout ter 1024 passos conjuntos. O horizonte é o mesmo; a estrutura de dados é que muda.

IPPO

learn() verifica any(len(buffer) < 1024) nos n buffers. Cada buffer tem 1024 transições; o update concatena 4096 com 4 agentes.

MAPPO

learn() verifica buffer.n_steps < 1024. São 1024 passos conjuntos, cada um com 4 transições; o total também é 4096.

atualização · GAE

GAE por agente, valores centralizados

O GAE continua sendo calculado por coluna: uma trajetória por agente, sem atravessar de um agente para outro. A diferença é que cada V vem do crítico centralizado.

crítico central → values (T, n) → Vi,t para cada agente

agente 1GAE backward

n_steps, n_agents = rewards.shape
for agent in range(n_agents):
    gae = 0
    for t in reversed(range(n_steps)):
        nonterminal = 1.0 - terminated[t, agent].float()
        delta = (rewards[t, agent]
                 + gamma * nonterminal * next_values[t, agent]
                 - values[t, agent])
        propagates = (1.0 - episode_ends[t, agent].float()) * nonterminal
        gae = delta + gamma * gae_lambda * propagates * gae
        advantages[t, agent] = gae
  • Mesma recorrência do PPO. A diferença é que values tem shape (T, n) e vem de joint_values.
  • Normalização conjunta. As vantagens são normalizadas sobre todas as T × n entradas, não por agente.
  • Retornos. returns = advantages + values; o crítico centralizado é o alvo do MSE.
◎O crítico não entra na ação. O ator usa forward(x) no update; o crítico só fornece o valor para o GAE e para a perda de valor.
atualização · minibatches

Minibatches de passos conjuntos

O MAPPO não sorteia transições soltas. Cada minibatch é um bloco de passos conjuntos: a CNN roda uma vez por agente e alimenta o ator e o crítico.

steps_per_batch = max(1, self.batch_size // n_agents)
...
mb_idx = idx.to(self.device)
mb_states = states[idx].to(self.device)   # (S, n, C, H, W)
mb_feats = self._features(mb_states)       # (S, n, F)
mb_logits = self.online.actor(mb_feats)
mb_values = self.online.joint_values(mb_feats)
SO batch_size é em transições. O código arredonda para baixo em blocos de passos: batch_size // n_agents. Com 64 e 4 agentes, cada minibatch tem 16 passos conjuntos = 64 transições.
!Um forward para os dois. _features achata (S, n, C, H, W) em (S·n, C, H, W), roda a CNN e devolve (S, n, F). O ator lê a mesma feature que o crítico.

atualização · perda

A perda e o valor recortado

A perda do ator é a mesma do PPO. A novidade opcional é o value_clip, que limita o passo do crítico em torno do valor antigo.

ratio = torch.exp(log_probs - old_log_probs[idx])
policy_loss = -torch.min(
    ratio * adv,
    torch.clamp(ratio, 1.0 - self.clip,
                1.0 + self.clip) * adv).mean()

if self.value_clip is None:
    value_loss = mse(mb_values, mb_returns)
else:
    old = values_old[mb_idx]
    clipped = old + torch.clamp(
        mb_values - old,
        -self.value_clip, self.value_clip)
    value_loss = torch.max(
        mse(mb_values, mb_returns),
        mse(clipped, mb_returns))

loss = policy_loss + 0.5 * value_loss - 0.01 * entropy

atualização · memória

Memória: rollout na CPU, blocos para a GPU

Um rollout de 1024 passos × 4 agentes com frame stack ocupa centenas de megabytes. Manter tudo no device junto com as ativações pode estourar uma GPU pequena.

CPUrollout inteiro
states, next_states, actions, rewards, terminated e episode_ends ficam aqui.
GPUum bloco por vez
chunks de eval_chunk_steps = 64 para recalcular log-probs e valores.
  • Recalcular em blocos. O _update varre o rollout em chunks de 64 passos, manda cada chunk para a GPU e traz log-probs/valores de volta para a CPU.
  • GAE na CPU. A recorrência é feita com os valores na CPU; só vantagens, retornos e os minibatches voltam ao device.
  • Um knob de memória. eval_chunk_steps não muda o algoritmo; muda o pico de memória e o número de transfers.
!O buffer não vai inteiro para a GPU. O minibatch é montado a partir do array na CPU e transferido só quando o bloco é usado. É o que permite treinar 4 agentes com frame stack em 6 GB.
→O contraste com o PPO. O PPO de um agente cabe no device; o MAPPO precisa desse cuidado porque o estado conjunto multiplica o rollout por n_agents.

prática · trade-offs

O que o MAPPO ganha e o que custa

O crítico centralizado compra variância menor com informação conjunta. O preço aparece na memória, no tamanho da entrada e na dependência da coleta.

Ganha

  • Valor mais informado. O crítico vê as features de todos os agentes e pode separar o efeito de uma jogada do aliado.
  • Identidade pelo one-hot. O mesmo estado conjunto pode gerar V diferentes para papéis e times diferentes.
  • Ator descentralizado. A política continua executável por agente, sem estado global.
  • Mesma estabilidade. O recorte, a entropia e o grad clip do PPO continuam no lugar.

Custa

  • Entrada que cresce. O crítico recebe n × 1280 + n: 5124 entradas com 4 agentes, 7686 com 6.
  • Memória. O rollout conjunto é maior; o update precisa de chunks para não estourar a GPU.
  • Dependência da coleta. O crítico centralizado exige as observações de todos no mesmo passo; não dá para treinar com um agente isolado.
  • Mesmos limites on-policy. Sem replay, sem --envs, sem --overlap, sem adversários baseline misturados.
!Neste mapa, o ganho é menor do que em POMDPs. A grade de cada agente já mostra todos os personagens. O que o MAPPO adiciona é o vetor conjunto de features, a identidade e a variância menor; em um mapa com observação parcial, o crítico centralizado veria informação que o ator não tem.
→Quando usar. Times com papéis diferentes, recompensa compartilhada e necessidade de um valor conjunto. Se os agentes são homogêneos e o orçamento é curto, o IPPO é mais simples.
crítico · identidade

Times e o one-hot

As mesmas features conjuntas alimentam todos os V. Sem identidade, o crítico não teria como dar valores diferentes ao agente 0 e ao agente 1. O one-hot é essa identidade.

agente consultadoone-hot
consultando a0 → o crítico devolve V0.

O one-hot entra concatenado às features; ele não muda o estado, só diz qual saída o crítico deve produzir.

  • Mesmo estado, saídas diferentes. O crítico devolve um V por agente. O one-hot permite que a mesma rede aprenda valores específicos de time ou papel.
  • Persistente = False. agent_onehot é um buffer derivado de n_agents; não entra no state_dict nem no checkpoint.
  • Em todos-contra-todos o one-hot é o único sinal de identidade. Em times, os canais 2 e 5 também mostram inimigos e aliados, mas não dizem qual membro é qual.
4Com 4 agentes, o crítico recebe 4 saídas: uma por linha do one-hot. O ator continua com uma saída por agente, calculada localmente.
integração · ciclo de vida

Checkpoint, avaliação e duelo

O MAPPO grava o mesmo formato pesos-only do IPPO, com o algoritmo e o cenário na config. A execução é descentralizada, então avaliar e assistir funcionam igual.

O que vai para o disco

  • algorithm = "mappo", arch_version = "alg-mappo-v1".
  • Pesos da rede única, otimizador, contadores e config com n_agents/team_ids.
  • Não vão: o buffer conjunto, o one-hot (derivável) e os RNGs.
✓Avaliação e espectador. evaluate.py usa act_batch(..., greedy=True) e grava uma linha por agente; play.py entra em modo espectador.
×Não mistura algoritmos. Um checkpoint MAPPO não carrega em IPPO ou PPO: o campo algorithm é validado. O cenário também não pode mudar na retomada.
duelo MAPPO × IPPO
python scripts/duel_multiagent.py \
  --mappo-checkpoint checkpoints/mappo_teams4_3h/best.pt \
  --ippo-checkpoint checkpoints/ippo_teams4_3h/best.pt \
  --mappo-team 0 \
  --record duelo.mp4
!Um checkpoint por time. O play.py só aceita um checkpoint multiagente (modo espectador). Para colocar MAPPO contra IPPO, o script de duelo carrega dois checkpoints, valida que o formato de observação e o cenário coincidem, e usa a política gulosa com seeds fixas.
2O duelo não treina. É uma avaliação pareada: MAPPO controla um time, IPPO controla os demais. O mesmo par de checkpoints e as mesmas seeds produzem o mesmo vídeo.

O que os testes cobrem

  • Crítico centralizado: V0 muda quando as features do agente 1 mudam.

  • Checkpoint: round-trip, config do cenário e incompatibilidade com IPPO.
  • CLI: --alg mappo aceita o cenário e recusa --envs, --overlap e --opponent fixo.
