visão geral · as cinco diferenças

O que muda quando o PPO vira multiagente

O núcleo do PPO continua: ator categórico, crítico, GAE, recorte e entropia. As diferenças estão em quem age, no que cada agente vê e em como os dados se organizam.

01 · ambienteUm env, N ações

ArenaEnv tem um aprendiz e um baseline; ArenaMultiEnv recebe um vetor de ações e devolve um vetor de recompensas.

02 · observação5 canais → 6 canais

Entram self, inimigos e aliados; cada agente tem o próprio frame stack.

03 · políticaUma rede para todos

Em vez de uma rede para o jogador, uma ActorCriticNetwork compartilhada por todos os agentes.

04 · bufferUm buffer por agente

MultiRolloutBuffer guarda uma trajetória por agente; o GAE é calculado separadamente.

05 · updateN × 1024 transições

O update só dispara quando todos os buffers enchem; as transições são concatenadas.

!Não são N redes independentes. O nome IPPO significa independent PPO, mas esta implementação compartilha os pesos: uma política é treinada com as transições de todos os agentes. O que é independente é a trajetória, não a rede.
→Próximo passo. Entender o ArenaMultiEnv, a grade de 6 canais e o contrato de buffers. O resto é o PPO que você já viu.
ambiente · passo conjunto

Um ambiente, N ações por step

No IPPO todos os personagens são controlados pelo algoritmo. O ambiente recebe um vetor de ações, avança a física e devolve um vetor de recompensas por agente.

obs, info = env.reset(seed=7 + ep)

while True:
    actions = agent.act_batch(obs)          # (n,)
    obs, rewards, term, trunc, info = env.step(actions)
    # rewards (n,), terminated (n,), truncated (n,)
    if np.all(trunc):
        break
nUma decisão por step. A ação de cada agente é mantida durante os frame_skip substeps de física. No single-agent, o adversário baseline re-decide a cada substep; aqui, não.
!Todos truncam juntos. O episódio acaba aos 45 s simulados para o vetor inteiro. Morte custa moedas e 5 s, mas não encerra nada.

política · parameter sharing

Uma rede para todos

Todos os agentes otimizam a mesma política. A observação relativa é o que permite papéis simétricos: o mesmo peso serve para quem persegue moedas e para quem empurra, desde que o canal certo esteja aceso.

# uma rede, um otimizador
self.online = ActorCriticNetwork(
    self.obs_shape, self.n_actions).to(self.device)
self.target = self.online   # sem rede-alvo
self.optimizer = Adam(self.online.parameters(), lr=lr)

# age no lote de agentes de uma vez

1×Um forward, não um loop. act_batch empilha as observações dos agentes e usa a mesma rede. O crítico também é compartilhado e local: V(s_i) usa só a observação daquele agente.

O que “independente” quer dizer

Cada agente aprende com a sua trajetória e trata os outros como parte do ambiente. O compartilhamento de pesos é uma escolha de implementação, não uma exigência do IPPO. Redes separadas seriam independentes de verdade, mas gastariam mais memória e amostras.

!Simetria não é especialização. A mesma rede não tem um parâmetro “eu sou o time 1”. Ela distingue papéis apenas pelo que os canais mostram. Em times, o MAPPO adiciona um one-hot no crítico para diferenciar o agente consultado.

Cenários e recompensa de time

O Scenario é a fonte única do cenário: quantos agentes existem e a que time cada um pertence. Em times, a recompensa de cada membro é a média do time.

recompensamédia por time

Mova a recompensa bruta de cada agente. O valor que cada membro recebe é a média do time.

!Em todos-contra-todos cada time tem um membro, então a média é a identidade. Em teams, a recompensa de um agente pode subir quando o aliado coleta uma moeda.
coleta · MultiRolloutBuffer

Um buffer por agente

O PPO tem um RolloutBuffer. O IPPO tem um por agente, dentro de MultiRolloutBuffer. O update só começa quando todos chegam a 1024.

# agent.py: o gatilho espera todos
def learn(self):
    if any(len(buffer) < self.rollout_steps
           for buffer in self.buffer.buffers):
        return None
    return self._update()

def end_episode(self, info=None):
    for i in range(self.n_agents):
        self.buffer.mark_episode_end(i)
  • Uma trajetória por agente. add(agent_index, ...) escolhe o buffer; o GAE de um agente não vê o do outro.
  • Uma fronteira por agente. mark_episode_end(i) marca o último passo daquele buffer.
  • Rabo do treino. finish_training() consome o rollout parcial de todos.
MultiRolloutBuffer0 updates
0 / 4096 transiçõesrollout_steps = 1024 / agente

Cada passo conjunto adiciona 1 transição a cada buffer. Enquanto algum estiver atrás, learn() devolve None.

=No loop real os buffers andam juntos: todo env.step adiciona exatamente uma transição por agente. O any() é uma rede de segurança; o caso de um buffer atrasado só apareceria em um coletor dessincronizado.

atualização · a mesma perda

O update continua sendo PPO

O recorte, a perda de valor e a entropia são os mesmos do PPO. O que muda é o lote: agora ele contém transições de todos os agentes.

ratio = torch.exp(log_probs - old_log_probs[idx])
unclipped = ratio * adv
clipped = torch.clamp(ratio, 1.0 - self.clip,
                      1.0 + self.clip) * adv
policy_loss = -torch.min(unclipped, clipped).mean()
value_loss = nn.functional.mse_loss(values, returns[idx])
entropy = dist.entropy().mean()
loss = (policy_loss + self.value_coef * value_loss
        - self.entropy_coef * entropy)

coleta · fim de episódio

Episódio e fronteiras

O ambiente multiagente trunca todos juntos aos 45 s. A morte custa moedas e 5 s, mas não encerra o episódio. O GAE respeita a marca de cada agente.

terminated

Fim verdadeiro. O código suporta, mas neste mapa nunca vira True: a morte respawna.

truncated

Fim por tempo, para o vetor inteiro. O alvo continua com o bootstrap γV(s′).

episode_end

Marca a última transição de cada buffer. O GAE do agente para ali, mas não dobra para o próximo.

O loop multiagente

O train.py troca o loop de um agente por um passo conjunto: age no lote, avança o ambiente, adiciona uma transição por agente e chama learn().

while True:
    actions = agent.act_batch(obs)
    next_obs, rewards, term, trunc, info = env.step(actions)
    for i in range(n_agents):
        agent.add_transition(
            i, obs[i], int(actions[i]), float(rewards[i]),
            next_obs[i], bool(term[i]))
    loss = agent.learn()
    obs = next_obs
    if np.all(trunc):
        break

agent.end_episode(info)   # marca os n buffers
  • Sem auto opponent. Não há adversário baseline: todos os personagens são controlados pela política.
  • Sem epsilon e sem warmup. A exploração é a categórica e a entropia, como no PPO.
  • Update a cada passo do loop? learn() é chamado sempre, mas só age quando todos os buffers têm 1024. O resto é coleta.
  • Fim do treino. finish_training() consome o rollout parcial antes do checkpoint final.
integração · restrições

Os limites da primeira versão

O modo multiagente é deliberadamente simples: um ambiente, todos os agentes no mesmo passo, sem coleta vetorizada e sem adversários misturados.

O que o CLI recusa

  • --envs > 1: a coleta vetorizada não sincroniza os buffers por agente.
  • --overlap: não há uma cópia da política coletando em paralelo.
  • --opponent rule|random|coins: todos os personagens aprendem; não sobra um baseline.
  • --agents < 2 e times indivisíveis: o cenário exige pelo menos dois agentes e times iguais.

O que isso implica

  • Um worker. A coleta é sequencial; a GPU espera o ambiente a cada passo conjunto.
  • Cenário fixo. --agents, --scenario e --teams não podem mudar ao retomar: o checkpoint valida n_agents e team_ids.
  • Um checkpoint, um elenco. O mesmo arquivo controla todos os agentes; play.py entra em modo espectador e recusa --player/--opponent.
!Por que começar assim. Um único ambiente deixa a semântica do passo conjunto e das recompensas de time fácil de auditar. Vetorizar exigiria workers sincronizados e uma política de merge dos buffers; o MAPPO herda a mesma restrição.
✓O que continua funcionando. --render, --record, --tensorboard, --stats, --max-hours e a retomada por checkpoint.

integração · ciclo de vida

Checkpoint e avaliação

O IPPO usa o mesmo formato pesos-only do PPO, mas grava o cenário na config. O checkpoint identifica o algoritmo e o elenco; a retomada não pode trocar nenhum dos dois.

O que vai para o disco

  • algorithm = "ippo", arch_version = "alg-ippo-v1".
  • Pesos de online e target (os mesmos), otimizador e contadores.
  • config com n_agents, team_ids, frame_stack e frame_skip.
  • Não vão: os n buffers, RNGs e estado do ambiente.
✓Avaliação. evaluate.py detecta n_agents > 1, usa ArenaMultiEnv e chama act_batch(..., greedy=True); grava uma linha por agente.

prática · trade-offs

O que o IPPO ganha e o que custa

A política compartilhada é simples e eficiente em amostras. O preço é a não-estacionariedade e a dificuldade de especializar papéis.

Ganha

  • Dados de todos, uma rede. Cada atualização usa as trajetórias de n agentes; a política compartilhada aproveita melhor as amostras.
  • Simetria. A grade relativa permite que o mesmo peso aprenda a perseguir e a empurrar sem duplicar a rede.
  • Menos peças. Um otimizador, uma rede, n buffers. Fácil de auditar e de retomar.
  • Escala para times. O cenário e a recompensa média funcionam para qualquer número de times iguais.

Custa

  • Não-estacionariedade. Cada agente trata os outros como ambiente; conforme eles mudam, o problema de cada um muda também.
  • Sem identidade explícita. A mesma rede não tem um parâmetro “sou o time 1”; papéis só aparecem pelos canais.
  • Crítico local. Em times, V(s_i) pode ter variância alta; o MAPPO troca por um crítico centralizado.
  • Recompensa média. O crédito de uma moeda do aliado chega a todos; pode borrar a atribuição individual.
→Quando usar. Muitos agentes homogêneos, papéis simétricos e computação limitada. Quando o valor de um agente depende do estado conjunto, ou quando os papéis precisam de valores diferentes, o MAPPO é o próximo passo.
